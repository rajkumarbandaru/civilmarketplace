Interview guide: describing this project

How to talk about billing_micro_services — a production telecom BSS — in an interview or design review. Scripts you can say out loud, the numbers to have ready, a whiteboard sequence, STAR stories built from real system behaviour, and answers to the questions this architecture invites. Every fact here was checked against the source; see 07-project-handbook.md for the full map.

01The pitch, in three lengths

Interviewers ask "tell me about your project" and then interrupt. Have a 30-second, a 2-minute, and a deep version — and stop at the end of each.

30 seconds

"I work on the BSS for a mobile virtual network operator — the system that sells the plan, activates the SIM, rates the usage, charges the customer, and talks to the carriers whose network we resell. It's a Java 8 / Spring Boot codebase, 117 Maven modules, around 49 Spring Boot applications with roughly 23 deployed on Kubernetes, MySQL per business domain, MongoDB for call records. I own subscriber-facing flows end to end: purchase, activation, recharge, billing."

2 minutes

"An MVNO doesn't own a network — it buys wholesale capacity and sells retail service, so the BSS is the business. Ours does five things: catalogue and ordering, subscriber lifecycle, money, usage rating, and carrier integration."

"A purchase creates an order and takes payment through Stripe or wallet, inventory allocates a SIM, shipment books a label. Activation writes a subscription, publishes an event, and one of three carrier gateways — Verizon, T-Mobile via a wholesale partner, or Tata — provisions the line and returns a number. Usage comes back as CDRs, which we collect, rate against the plan's buckets and post to the ledger. Recharges and monthly invoices move money through the wallet and the general ledger."

"The interesting part is the constraints. The event bus is a polled MySQL table, not a broker. There's no migration tool — Hibernate updates the schema on deploy. There's no rollback stage, and almost no automated tests. So the engineering discipline is front-loaded: trace every consumer before you change a shared module, keep schema changes additive, and verify manually against a named list of affected services."

Deep version — the 10-minute walkthrough

Structure it as: domain → architecture → one flow in detail → a hard problem → what you'd change.

  1. Domain (1 min). MVNO economics: we carry the customer relationship, the carrier carries the packets. That's why carrier integration and rating accuracy are the two places bugs cost real money.
  2. Architecture (2 min). Use the whiteboard sequence in section 3. Be honest that it's a distributed monolith: deployment boundaries are real, data boundaries aren't.
  3. One flow (3 min). Pick recharge or activation and narrate it step by step with the actual service names.
  4. A hard problem (3 min). Idempotency across replicas, or carrier fan-out, or a schema change under ddl-auto. Show the reasoning, not the outcome only.
  5. What you'd change (1 min). Three specific improvements with blast radius attached (section 7).
Rule of thumbLead with the business, not the framework list. "It bills real subscribers for real usage" earns more attention than "Spring Boot microservices with Spring Cloud Config".

Narration script. "Money enters on the left through self-service payment. The subscriber record lives in user-management. Anything that needs to happen elsewhere is written as a row in an events table that every other service polls — that's our bus. Activation fans out to three carrier gateways; each one filters on the subscriber's carrier, which was decided earlier by which SIM stock was allocated. Usage comes back as CDRs, gets rated against the plan's buckets, and lands in MySQL for billing while the raw volume stays in Mongo."

Why this drawing worksIt shows a data flow, a fan-out, a feedback loop, and a deliberate trade-off (table-as-bus) in about ninety seconds. That's four things to be asked about — all of which you can answer.

04Flows you can narrate end to end

Pick one and know it cold. Each has a "what makes it interesting" line — that's the hook that turns a description into a discussion.

Purchase → fulfilment

Browse catalogue → price and tax → pay by card (Stripe) or wallet → order rows written → SIM allocated from inventory → shipping label booked with USPS/UPS → confirmation email.

Interesting because: the payment webhook and the order creation are separate, asynchronous events, so the order must be created idempotently — the same webhook can arrive twice, and a retry must not create a second order or allocate a second SIM.

Activation

SIM/eSIM submitted → subscription and SIM records written in a pre-active state → ACTIVATED event → the right carrier gateway provisions the line and returns a mobile number → subscription flips to active → welcome SMS/email.

Interesting because: it's a distributed state machine over an external system you don't control. The carrier call can time out after succeeding on their side, so "retry" and "duplicate provisioning" are the same action unless the state check is authoritative.

Recharge / top-up

Payment validated and routed → gateway dispatch → webhook confirms → prepaid record written → bundle-activation event → carrier applies the bucket → balance and expiry visible to the customer.

Interesting because: money moves before the network changes. If the carrier step fails after the charge succeeds, you owe the customer either a bucket or a refund — which is exactly the compensation problem interviewers like.

Usage / CDR rating

Carrier drops or exposes usage records → scheduled collection → parse and bulk insert → rate each record against the subscriber's active buckets → decrement balance, post revenue.

Interesting because: it's the only high-volume path in the system, it's batch rather than request/response, and duplicates are silent — a double-inserted CDR bills the customer twice and nothing throws.

Postpaid billing and dunning

Monthly cron raises invoices → invoice event → notification service emails the invoice and sends a per-carrier SMS → unpaid invoices are chased on a recurring dunning cycle → GL postings for revenue and tax.

Interesting because: crons here have no distributed lock, so with more than one replica the same invoice run can fire twice — a concrete example of why "just scale it out" isn't free.

05STAR stories

Behavioural rounds want Situation / Task / Action / Result. These four are built from how the system actually behaves — fill in your own specifics where marked.

Story 1 — "Tell me about a bug that was hard to find"

S. A customer was charged but the bundle never appeared on the line. No exception in any log, no alert.

T. Find out where the chain broke, in a system with no distributed tracing and no correlation IDs.

A. I worked backwards from the money: confirmed the payment row, then the prepaid record, then looked for the event row in the events table. It was there and marked processed — but the carrier call inside the handler had thrown, and the handler marks the row processed after a single attempt regardless of outcome, so the failure was swallowed. I correlated by MDN and timestamp across services to prove it.

R. Reprocessed the affected subscribers, and raised the general problem: at-least-once delivery with no retry and no dead-letter means a transient carrier timeout silently loses a paid-for entitlement. [Add what you actually shipped — a replay path, a reconciliation check, an alert.]

Shows: methodical debugging without tooling, reading the mechanism rather than guessing, separating the incident from the systemic cause.

Story 2 — "Tell me about a change you made carefully"

S. A one-field change to an entity in a shared repository module — the kind of thing that looks like a five-minute task.

T. Ship it without breaking other services.

A. That module is compiled into a dozen other applications, and the schema is evolved by Hibernate on deploy, so the change would apply itself to production with no migration script and no way to drop the column afterwards. I grepped every module that declares the dependency, checked which of them read or write that table, confirmed the change was purely additive, and checked whether the field crossed an API response or an event payload — there's no API versioning, so a shape change hits every client at once.

R. Shipped additively, with the affected services named in the PR and verified manually after deploy, because a green build here only proves compilation.

Shows: you understand blast radius, irreversibility, and that "small diff" is not "small change".

Story 3 — "Tell me about a design decision you disagreed with"

S. The async bus is a MySQL table that every service polls, while a full RabbitMQ implementation sits unused in the codebase.

T. Decide whether to push for switching.

A. I read both paths instead of assuming the broker was better. The Rabbit path as written acknowledges before processing, on a non-durable queue with no dead-letter exchange — so switching would have given us weaker delivery guarantees than the table, not stronger. The table is durable, inspectable with SQL, and survives restarts; what it lacks is retry, a DLQ, and safe concurrent consumption.

R. I argued for fixing the gaps we actually have — retry with backoff, a dead-letter state, and a locked or conditional claim so two replicas can't grab the same row — rather than a migration that would have looked modern and regressed reliability.

Shows: you evaluate rather than pattern-match, and you can disagree with a framework fashion for stated reasons.

Story 4 — "Tell me about working with an external partner"

S. Three carrier integrations — Verizon, a wholesale T-Mobile partner, and Tata — each with a different protocol style (SOAP, REST, OAuth2 client credentials) and very different maturity.

T. Make a change to provisioning behaviour without breaking a live carrier contract.

A. I treated them as three separate systems rather than one abstraction. The newest integration had no circuit breaker, no effective timeout and no retry coverage, so behaviour verified against one carrier told me nothing about the others. I checked each carrier's code path independently and kept the fix inside the carrier-specific module rather than in shared code.

R. The change shipped for the carrier that needed it, with the other two provably untouched. [Add your specifics.]

Shows: you resist premature abstraction, and you understand that an external contract breaks differently from an internal one.

06Hard questions, strong answers

This architecture invites specific questions. Prepare these six and you'll rarely be surprised.

"How do you stop a customer being charged twice?"

"Three layers, and only one of them actually holds across replicas. The gateway gives us a durable dedup key on the webhook. The database state check — has this payment already moved to confirmed — is the real guard, because it's a single source of truth every pod sees. There are also in-process locks in the code, but they're JVM-local, so with more than one replica they protect nothing; I'd never rely on them. If I were adding a new money-moving path today I'd give it a unique constraint at the database level, because that's the only mechanism that can't be raced."

"You have almost no tests. How do you ship safely?"

"By moving the verification earlier, and being explicit about what isn't verified. Before a change I identify every consumer of what I'm touching — module dependencies, shared tables, event payloads, config keys — and say so in the PR. After deploy we have Python verifier scripts that check real database and API state for the payment and fulfilment flows, plus around a hundred scheduled validation scripts that alert on duplicate charges, stuck CDRs and failed activations. It's post-hoc detection, not prevention, and I'd say that plainly: a green build means it compiled. Where I've added code, I've kept it small and reversible rather than clever."

"How do you handle schema changes without migrations?"

"Carefully and additively. Hibernate is set to update everywhere, so an entity change becomes a DDL statement on the next deploy — no review step, no rollback, and columns are never dropped. Practically that means: add nullable columns, never rename, never repurpose an existing column, and check every other service that embeds the same repository module, because several applications share one schema. It's the constraint I'd most want to fix, with a real migration tool and a review gate."

"Why a database table instead of Kafka?"

"History rather than design, but it has real properties: events are durable, transactional with the business write, and you can inspect and replay them with SQL, which matters a lot during a billing incident. What it costs you is throughput, a retry policy, dead-lettering, and safe concurrent consumption — the claim is an unlocked select, so two replicas can double-process. If I moved it to a broker I'd do it consumer by consumer behind the same interface, starting with the lowest-risk topic, rather than as a big-bang switch."

"What would you fix first, and why?"
  1. Retry and dead-lettering on the event bus — today a handler that throws loses a paid-for entitlement silently. Highest customer impact per unit of work.
  2. A distributed lock for crons and stock allocation — the correctness bugs that appear the moment you scale past one replica, which is exactly when you least want them.
  3. Correlation IDs — cheap, unlocks every future investigation, and there's nothing to break.

"Each of those is scoped, has a blast radius I can describe, and doesn't require rewriting anything."

"Is this really microservices?"

"Honestly, no — it's a distributed monolith, and I'd rather say that than defend a label. The deployment boundaries are real: services are built, released and scaled independently. The data boundaries aren't: one application opens connection pools into a dozen other domains' schemas. So we get the operational cost of distribution and only some of the benefit. Knowing that changes how I work — I check the shared table, not just the shared class."

08How to talk about the weaknesses

This codebase has real problems. Naming them well is a strength; either hiding them or trashing the team is a weakness.

Say

  • "The constraint is X, so the discipline we apply is Y."
  • "I'd fix it in this order, for these reasons."
  • "That's a known trade-off; here's what it costs us."
  • "I verified that against the source before relying on it."
  • "I don't know — I'd check the Jenkins service map."

Don't say

  • "The codebase is a mess." (No judgement shown, and it's your work too.)
  • "We'd just move it to Kafka/microservices/the cloud." (Unscoped.)
  • Anything with a credential, customer record, or internal hostname in it.
  • Invented metrics — traffic, revenue, uptime you never measured.
  • "There are no tests, so nobody knows if it works." (True-ish, useless.)
ConfidentialityDescribe architecture, patterns and your reasoning — never paste proprietary code, real subscriber data, carrier contract terms, internal hostnames or credentials into an interview, a take-home, or a portfolio. Everything in this guide is safe to say out loud; that's deliberate.
