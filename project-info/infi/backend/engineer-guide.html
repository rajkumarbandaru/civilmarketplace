Engineer's guide: owning this system at ~5 years' experience

A practical handbook for working in billing_micro_services: getting oriented, shipping changes safely, debugging production, and explaining the system. It assumes you've seen the flow walkthroughs. The checklists remember what you tick.

01What's different here

You already know Spring Boot. These seven differences are what actually decide whether your change is safe.

02Your first week

~117 modules and ~49 services. Don't read them: learn one vertical slice and the rest becomes pattern-matching.

DAY 1-2Follow the money. Read the purchase and recharge walkthroughs, then CustomerSelfRechargeController (skim, ~9,000 lines) → PaymentFacade (the newer, clean design) → OrderFulfillmentServiceImpl. This one path shows both generations of style side by side.

DAY 3Learn the event bus. event-mgmt-utils's EventService, any *EventHooks class, and RMQEventRepository's polling query. A producer writes a row; every subscriber polls and filters.

DAY 4Learn one carrier path. mno_mgmt is the most complete: activateSubscriber → allocateMnoSubscriptionReference → mno-gateway-api. Every carrier integration is shaped like it.

DAY 5Learn where truth lives. .claude/INDEX.md routes you to discovery docs per topic — a map, not gospel. They're dated snapshots and some claims are stale (see section 08).

The habit that mattersBefore you rely on a fact, confirm it with grep: every caller of a method, every reader and writer of a table.

04Task recipes

The six changes you'll most often be asked for, and the trap in each.

Add a field to an API response

Find the DTO, add the field, check every consumer (mobile app, web, another service, marketplace integration). There is no API versioning, so the change hits 100% of traffic at deploy. Additive is safe; renaming or removing is not.

Add a column to an entity

Additive only. On deploy, Hibernate adds the column to production; removing a field later leaves an orphaned column forever. Check whether another service maps the same table — several are shared, and both entity definitions must agree.

Add a new event consumer

Implement the relevant on*Event in your service's EventHooks, register the topic in its subscription list, and filter by mnoSimProfile if the event is carrier-specific — this is exactly where the GUPI handler goes wrong. Assume your handler can be called twice, and that if it throws, the event is gone.

Add a new payment product type

Follow the existing shape: add to SelfPaymentTypes, add a case to PaymentFacade's dispatch switch, implement the fulfilment method in OrderFulfillmentService. Reuse the validator chain instead of adding inline checks.

Add a scheduled job

There's no distributed lock (no ShedLock, no clustered Quartz). With more than one replica your cron runs on all of them. Either make the work idempotent, or claim it in the database (a status update with a WHERE on the previous status).

Change a carrier's behaviour

Put it in that carrier's module (mno_mgmt, pwg-mno-mgmt, gupi_mgmt), never in shared code. A carrier fix applied to a shared module is the exact pattern that has caused cross-carrier regressions here.

05Debugging playbooks

There is no correlation ID and no tracing. You follow business keys: transaction token, recharge token, ICCID, MSISDN, order number.

"The customer paid but got nothing"
  1. Find gateway_transaction by transaction token or gateway reference; read transaction_status.
  2. transactionStarted → the webhook never arrived or failed. Check webhook_events.
  3. transactionComplete but no order → fulfilment after confirmation failed. For a card SIM purchase the order is created by user-management from the SUBMIT_ORDER event: check payment_order_info (is_ordersubmitted, failure_cause) and whether the event row exists in rmq_events.
  4. No event row, or a row nobody consumed → nothing will retry it. Manual intervention or a replay endpoint is needed.
"Activation is stuck"
  1. subscription.activation_state + sim_info.lifecycle_state show how far it got. PreActive = the platform did its part, the carrier hasn't confirmed.
  2. Check mno_subscription for order_ref_no and failure_cause, then failed_mno_subscription.
  3. Check routing: handlers filter on carrier, so a wrong mno_sim_profile on the stock row means no carrier service acted.
  4. Remember the duplicate guard is per-pod: two activations for one ICCID can both proceed.
"The event didn't get processed"

Check rmq_events for the row and its timestamp. Consumers poll by a time window, so a slow or restarted consumer can miss it. There's no DLQ: if a handler threw, the event is marked processed and gone. Fix forward by re-publishing or via an admin endpoint.

"Usage / CDR data is missing"

Collection is a chain of scheduled jobs with a pod-local folder in the middle. Check in order: did the collector cron run, is the file in the folder, did the parse cron move it, did the insert cron write to MongoDB, is there a record-index row. A pod restart mid-chain can strand files.

What you have to work with

Logs are mostly unstructured log4j and System.out. JavaMelody (/monitoring) is the per-service APM. Python verifier scripts detect problems after the fact (duplicate charges, stuck CDRs, failed activations). Actuator/Prometheus endpoints are exposed but have no confirmed scraper and no business metrics.

06Risk radar

Things that should make you slow down and widen the analysis.

Shared/common modulesbilling-util, billing-common-repository, billing-repostiory, event-mgmt-utils. High fan-in: any change is platform-wide.
SubscriptionEvent.UpdateFlagAn ordinal-positional bitmask. Inserting or reordering a value anywhere but the end silently corrupts every consumer, with no compile error.
Money pathsWallet debit and the local insert aren't atomic; wallet and ledger can disagree.
SIM allocationNo locking: concurrent orders can take the same stock.
Static mutable stateCorrect on one pod, wrong on two. Duplicate guards, rate limiters and idempotency maps are all in-JVM.
Security-adjacent changes"Fixing" the no-op permission check changes behaviour at ~1,000 call sites at once. That's a project, not a bug fix.
Duplicated classesTwo CryptoHelpers, two carrier enums, two UserAddressCommands. Assume a duplicate drifted for a reason; check both.

07Operating in production

  • Deploys: a manually parameterized Jenkins job per service. Build (mvn -pl <module> -am clean install) → Deploy (build_run.sh on a Docker host, then kubectl from a jump host).
  • Config: comes from config-server at boot; if it's down, services don't start. Two carrier modules bypass it with their own properties.
  • Rollback: not a pipeline step. Plan fix-forward and keep schema changes additive.
  • Recovery: for a stuck cron, failed CDR batch or lost event it's largely manual, sometimes a database edit. If that's the honest answer for your change, put it in the ticket.
  • Monitoring: JavaMelody plus after-the-fact Python verifiers. No business metrics, no tracing.

08Don't trust documentation — including this

Everything here was verified against source. Doing that verification found several wrong claims in the repo's own notes.

The habitCite file:line, and re-check before relying on it. When you correct something, correct it everywhere it's repeated — otherwise the stale copy misleads the next person.

09Explaining this system

For interviews and design reviews. These land because they show judgement, not a feature list.

"A telecom BSS: ~117 Maven modules, ~49 Spring Boot services, MySQL per domain, MongoDB for call records, on Kubernetes. I owned the subscriber journey end to end — purchase, activation, recharge." Scale and shape, in one breath.
"Async between services is a polled MySQL table rather than a broker. Events are durable and easy to inspect, but there's no retry or dead-letter, so consumers must be idempotent and failures need a replay path." A non-obvious design decision, with its trade-off.
"Payment confirmation is idempotent through a state check plus a durable webhook dedup key. The in-process lock only protects one pod, so the database state check is what actually makes it safe across replicas." A concrete correctness problem you can reason about.
"One activation event fans out to three carrier services, each filtering on the subscriber's carrier — which was decided earlier, by which SIM stock was allocated." Integration design.
"No migration tool and ddl-auto=update, so schema changes are additive and irreversible; no rollback stage, so we plan fix-forward; near-zero tests, so changes are scoped tightly and verified manually against named consumers." Operating under constraint.
"What I'd fix first: idempotency and a retry/DLQ path on the event bus; a distributed lock for crons and SIM allocation; enforcing the API-key check that's currently computed and ignored; correlation IDs." Specific, defensible improvements with a blast radius you can describe.
The signal at this levelNot "I know Spring Boot", but: "I can tell you exactly what happens if this call fails, who else depends on it, and how I'd verify it in a codebase with no tests."
